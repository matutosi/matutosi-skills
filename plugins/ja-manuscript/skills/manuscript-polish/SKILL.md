# 書籍入稿前 原稿推敲スキル

## 目的

Markdown形式の原稿を入稿前に推敲し、編集者が受け取ったときの修正負担を最小化する。出力は問題点リストと修正案の差分表。

---

## チェック項目

対象ファイルを順に読み、以下の5項目を確認する。

### 1. 誤字・脱字

- 明らかな誤字・脱字・変換ミスを検出する
- 助詞の誤り (「をが」「はが」など) も対象
- 固有名詞・専門用語の誤りも含む

### 2. 表記ゆれ

同じ意味・対象を複数の表記で書いている箇所を検出する。以下は代表的なパターン:

- 送り仮名: 「受け取る/受取る」「申し込み/申込み」
- 漢字・ひらがなの混在: 「事/こと」「時/とき」「為/ため」「所/ところ」「様/よう」
- 同義の語句: 「申請書/申請書類」「審査委員/審査員」「研究課題/課題」
- 括弧: 丸括弧は半角 `(` `)` に統一 (全角 `（` `）` は指摘)
- 数字: 全角数字と半角数字の混在

表記ゆれは **ファイル内** と **ファイル間** の両方を確認する。複数ファイルを横断するときは、最初に全ファイルの用語リストを把握してから比較する。

### 3. 文体の統一

- 「だ・である」体と「です・ます」体の混在を検出する
- コラムや図のキャプションは文体が異なる場合があるため、本文と区別して報告する
- 同一節内での混在を優先的に報告する

### 4. 書式の一貫性

- 見出しレベルの飛び (`#` の次が `###` など) を検出する
- 箇条書きスタイルの混在 (`-` と `*` の混在など)
- 図の挿入形式が統一されているか (`<img src="...">` の属性の一貫性)
- 表の列揃え記法の統一 (`:---` / `:---:` / `---:`)
- ページ区切り (`<div style="page-break-before:always"></div>`) の位置が適切か

### 5. 参照・相互参照の整合性

- `\@ref(ラベル)` の参照先が実際に存在するか確認する
  - ラベルは `{#ラベル}` の形式で見出しに付与されている
  - 参照先が見つからないものは「未解決参照」として報告
- 図の参照 (`図．ファイル名`) と実際の画像ファイル名の対応を確認する
- 表・図のキャプションが本文中の参照と一致するか

## 出力形式

### 問題点リスト

カテゴリ別に整理して出力する。各指摘は以下の形式:

```
- **[ファイル名:行番号付近]** 問題の説明
  - 現在: `該当箇所の原文`
  - 修正案: `修正後の文`
```

深刻度を3段階で示す:
- `[要修正]` — 明確な誤りで必ず直す必要があるもの
- `[要検討]` — 表記ゆれや文体など、方針次第のもの
- `[確認]` — 参照先の存在確認など、事実確認が必要なもの

ほかのスキルの言い方との対応 (同じ重さを別の言葉で呼んでいる):

| このスキル | polish-loop の severity | apply-proof-marks の分け方 |
|---|---|---|
| `[要修正]` | 高 | 単純な修正 |
| `[要検討]` | 中 | 判断が要るもの (1 件ずつ) |
| `[確認]` | 低 | 判断が要るもの (事実確認) |

### 差分表

指摘が多い場合は、カテゴリごとに表でまとめる。

**パディングの規則:** 列幅を内容に合わせてスペースで揃え、人間がテキストエディタで見たときに縦が揃うようにする。日本語（全角）文字は半角2文字分の幅として計算する。

```
| 場所                  | 現在の表記                   | 修正案                          | 種別   |
|:----------------------|:-----------------------------|:--------------------------------|:-------|
| chapter_03.md(371)    | `状況は審査委員によって状況は` | `審査委員によって状況は`          | 要修正 |
| chapter_05.md(30)     | `fig_05_enphasis.png`        | `fig_05_emphasis.png`           | 要修正 |
| chapter_03.md(382)    | `その時には`                  | `そのときには`                   | 要検討 |
```

列幅の目安:
- 「場所」列: ファイル名+行番号で 22〜25 文字程度
- 「現在の表記」列: 内容に合わせて調整
- 「修正案」列: 内容に合わせて調整
- 「種別」列: 「要修正」「要検討」「確認」の最長に合わせる

## 手順

1. **対象ファイルを把握する** — ユーザーが指定したファイル、または `_bookdown.yml` からアクティブなファイルリストを取得する
2. **各ファイルを順に読む** — 5項目のチェックリストに従って問題を収集する。複数ファイルの場合は全ファイルを読んでから表記ゆれを横断チェックする
3. **問題点リストを出力する** — カテゴリ別・深刻度別に整理して出力する
4. **差分表を出力する** — 指摘が5件以上ある場合は差分表でまとめる
5. **修正の承認をもらうときは，提示の単位を守る** — 一覧と保存は全件をまとめて出すが，原稿へ反映する前に
   採否を聞くときは，**単純な修正 (`[要修正]`) は 5 件程度ずつ，判断が要るもの (`[要検討]`・`[確認]`) は 1 件ずつ**出す．
   ユーザが単位を指定していなければ，最初に既定の単位を示し，**変えられることを1行で伝える**
   (例: 「要修正は 5 件ずつ，要検討は 1 件ずつ確認します．『10 件ずつ』『全部まとめて』のように変えられます．」)．
   判断が要るものには案 a/b/c を付け，おすすめを a に置く．
   採否を聞く表は，apply-proof-marks と同じ `修正内容 | 修正前 | 修正後` の 3 列にする (保存するファイルは 4 列のままでよい)．

---

## 出力順序

チェック項目の番号 (1=誤字、2=表記ゆれ、3=文体、4=書式、5=参照) を基準に、出力先によって順序を変える。

**ファイルへの保存:** 5 → 4 → 3 → 1 → 2 の順
- スキル実行後、会話への表示と**同時に必ずファイルへも保存する**。ユーザーが「ファイルに出力して」と言わなくても自動で保存すること。
- 構造的・重大な問題 (参照→書式→文体) を先頭に置き、細かい表記の問題 (誤字→表記ゆれ) を後半にまとめる
- 編集者が優先順位をつけやすい構成にする
- ファイル名は `yyyymmdd_polish_result.md` の形式で、実行日の日付を使う (例: `20260630_polish_result.md`)
- ユーザーが明示的に別のファイル名を指定した場合はそちらを優先する
- ファイルの保存先はプロジェクトのルートディレクトリ (`_bookdown.yml` があるディレクトリ、またはユーザーが指定したディレクトリ)
- 保存完了後、ファイルパスを会話中で伝える

## 注意事項

- 表のカラム幅を統一
- Markdown記法 (`#`, `*`, `-`, `>` など) 自体は誤りとみなさない
- HTML タグ (`<img>`, `<div>` など) はこの原稿の仕様とみなし、存在自体は指摘しない
- `<!-- コメント -->` 内の記述はチェック対象外
- YAML frontmatter (`---` で囲まれた部分) はチェック対象外
- `\@ref()` の参照先確認は、現在開いているファイル群の中でのみ行う
- 修正案は提案であり、著者の意図を変えない範囲で示す
- TODO表記は最後にまとめる

## スキルを直す仕組み

実行中に「このスキルの手順・表・スクリプトでは足りない」と気づいたら，**報告の前に直すかどうかを決める**．

### 直す対象になる場面

| 場面 | 直す場所 |
|---|---|
| 検出できない誤り・誤検出に出会った | 「チェック項目」の該当の表に1行足す |
| 問題点リストの形が読みにくい | 「出力形式」を直す |
| 手順が分かりにくく，聞き返しが起きた | 「手順」を直す |

### 進め方

1. **まず今回の作業を終わらせる**．直すのは成果を渡したあと (作業を止めない)．
2. 直す内容を**番号つきで1行ずつ**ユーザに示し，「どれを入れるか」を聞く (選択肢の記号は `a`/`b`/`c`)．
   ユーザが「全部」「1と3」などと答えたものだけ直す．小さな追記 (表に1行・誤字) は，直したあとに報告するだけでよい．
3. **直す先**:
   - `matutosi-skills` のクローンが手元にあれば，その `plugins/ja-manuscript/skills/manuscript-polish/` を直す (場所はユーザに聞く．無理に探さない)．
   - 無ければ，インストール済みのプラグインは更新で消えるので**直接は直さない**．
     改善メモを成果と同じディレクトリに `manuscript-polish_improvements.md` として書き (場面・今回どうしたか・直す提案)，その場所を報告する．
4. 直すのは文書 (`SKILL.md`) だけで，版は上げない．再現する例は `evals/` に足す．
5. 直した内容と，まだ直していない提案を最後の報告に分けて書く．

### 直すときの決まり

- **実物の原稿・データ・地名・氏名をスキルに書かない**．パターンは一般化して書く．
- 例として `examples/` に足すときは架空のデータにする．
- 表に1行足すより，既存の行に当てはまらないかを先に確かめる (同じ内容を2か所に書かない)．
- **既定を黙って変えない**．既定を変えるときはユーザに確かめる．

## examples で試すとき

ユーザが「example で試したい」「サンプルで動かして」「見本で実行して」と言ったときは，**見本だからと手順を省かず，通常の実行と同じ流れで進める**．

- **通常と同じ確認 (質問・選択肢) を先に示す**．既定で進めてよいのは，ユーザが「既定で」「おまかせ」と言ったときだけ．
- 例は原稿を書き換えるので，**`examples/` を別の場所に写してから**試す．手順と成功の目安は `examples/README.md` の「スキルごとの試し方」に従う．
- 終わったら，`examples/README.md` の「`chapter_01.md` に入れた誤り」の表と照らし，挙がらなかった誤りを報告する．
