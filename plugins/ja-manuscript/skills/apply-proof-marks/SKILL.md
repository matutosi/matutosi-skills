# 校正 PDF の朱書きを原稿に反映する

タブレット等で PDF に手書きした校正(`/Ink` 注釈)を、章ごとに原稿へ反映する。

## なぜこの手順か

素朴にやると**校正ページを丸ごと画像で読む**ことになり、消費が大きい。
このスキルは2点で節約する。

1. **朱書きの位置を PDF の `/Ink` 注釈から取る。** 色で探すと、図の viridis や
   matplotlib の緑を朱書きと取り違える(実測で 122ページ中 10ページが誤検出だった)。
   注釈座標なら誤検出はゼロ。
2. **朱書きの周辺だけを切り出す。** ページ全体ではなく、朱書きのある帯に上下の文脈を
   足した画像だけを読む。実測でページ面積の **31%** に収まる。

**実測**(第5章 = p.56〜71 の16ページ、170dpi)。

| | ページ全体を読む | このスキル |
| --- | ---: | ---: |
| 画像 | 16枚(1178×1674) | 22帯(1178×102〜635) |
| トークン | 42,068 | **7,095** |

**17%(83%削減)**。16ページ中5ページには朱書きが1つも無く、そこを丸ごと外せるのが効く。
3層(素・clean・ink)を全帯で出しても 16,460(39%)なので、迷ったら出してよい。

**見つける朱書きの数は変わらない**(この16ページでは両者とも22箇所)。差が出るのは
**読み取りの確度**で、字に重なった朱書きは `_clean`／`_ink` が無いと確定できない。

## 手順

**作業の進め方 (既定．以下の手順のどこでも守る)**

1. **読み取りは先読みのエージェントに分ける．** 帯を切り出したら，本体が読むのは最初の表に要る分 (単純な修正 5 件程度) だけにする．残りの帯を本体が全部読まない．
2. **先読みは「次の 1 回分」だけ** (単純な修正 5 件程度，または要判断 1 件)．章や本全体を先読みしない．返事で方針が変わると，先に作った分が無駄になり，読み違いの手戻りも増えるため (4.2 節)．
3. **最初の表を出す前に，次の 1 回分の先読みを起動する．** 表を出して返事を待つだけでターンを終えない．
4. **採否の反映は別エージェントに任せ，そのあいだに次の分を出す** (4.2.1 節)．本体が置換を直接当てない．

- **コミット・push の扱いは，プロジェクトの規則 (CLAUDE.md など) に従う。定めが無ければ，作業を始める前に1回聞く** (polish-loop・rewrite-improve も同じ)。

### 1. 校正 PDF が現在の原稿と対応しているか確かめる

**校正 PDF は古いビルドのことが多い。** 直す前に、朱書きの対象文字列が
現在の原稿にあるかを `grep` で確かめる。無ければ「対応済み」と報告する。

```bash
python -c "from pypdf import PdfReader; print(len(PdfReader('_review/manuscript.pdf').pages))"
```

ページ数が手元のビルドと違えば、まず古いと疑う。

### 2. 朱書きの一覧を出す

```bash
python ${CLAUDE_SKILL_DIR}/scripts/extract_marks.py _review/manuscript.pdf --list
```

ページ番号の一覧と、帯(朱書きのかたまり)の本数が出る。ここで章ごとの分量が読める。

### 3. 章の範囲だけ切り出して読む

(読むのは，最初の表に要る分だけ．残りの帯は，上の「作業の進め方」の 1・2 のとおり先読みのエージェントに頼む．)

章の切れ目は、本文のコード ID を検索すると分かる。

```bash
python -c "
import sys; sys.stdout.reconfigure(encoding='utf-8')
from pypdf import PdfReader
t = [p.extract_text() or '' for p in PdfReader('_review/manuscript.pdf').pages]
for c in ['code_05_01_R', 'code_06_01_R']:
    print(c, [i+1 for i,p in enumerate(t) if c in p][:1])"
```

日本語は文字化けすることがあるが、**コード ID・節番号・英数字は拾える**ので位置決めに使える。

```bash
python ${CLAUDE_SKILL_DIR}/scripts/extract_marks.py \
    _review/manuscript.pdf --pages 56-71
```

`_review/marks/pNNN_bK.png` を Read で読む。**1帯=1画像**なので、
ページ全体を読み直したり拡大し直したりしない。

#### 朱書きが本文の字に重なっているとき

**重なるのが普通**なので、これは例外処理ではない。1つの帯につき最大3枚が出る。

| ファイル            | 中身                       | 何が読めるか                     |
| ------------------- | -------------------------- | -------------------------------- |
| `pNNN_bK.png`       | 朱書き入り(そのまま)       | **どの字に何をしたか**(位置関係) |
| `pNNN_bK_clean.png` | 朱書きを消した版           | **元の本文**(消された字も完全)   |
| `pNNN_bK_ink.png`   | 朱書きだけを白地に置いた版 | **手書きの文字**(本文と混ざらない) |

`_clean.png` は画像から緑を消したのではなく、**PDF から `/Annots` を外して描画し直した
もの**。`_ink.png` はその2枚の差分。どちらも本文と朱書きが完全に分離しているので、
重なっていても読み取りの精度は落ちない。

**3枚を突き合わせて読む。**「元の文字」は clean、「書き込んだ文字」は ink、
「どこに入れるか(挿入記号の行き先・取り消し線の範囲)」は素の帯で見る。

`--clean auto` / `--ink auto` は**筆跡ごとの重なり率**で判定する。迷ったら
`--clean always --ink always` にしてよい(出力が増えるだけで害はない)。

手書き自体が読めないときは `--zoom` を足すと、書き込み1つごとに 300dpi の拡大
(`pNNN_zJ.png`)が出る。挿入記号がどの語を指しているかは、たいていこれで決まる。

### 4. 修正案を表で出して承認をもらう

**提示の単位 (既定)**: **単純な修正は 5 件程度ずつ，要判断は 1 件ずつ**出す．
- ユーザが単位を指定していなければ，最初の提示の冒頭で既定の単位を示し，**変えられることを1行で伝える**
  (例: 「単純な修正は 5 件ずつ，要判断は 1 件ずつ出します．『10 件ずつ』『全部まとめて』のように変えられます．」)．
- 指定があればそれに従い，その作業のあいだは同じ単位を保つ．
- 要判断の出し方は 4.1 節の 8 (帯の画像を送り，案 a/b/c を付ける) と同じ．

**表の列は `修正内容 | 修正前 | 修正後` の3つ**にする。
ページの列は出さない (位置は自分で控える)。

- 「修正内容」は「◯◯を削除」「◯◯の前に△△を追加」「◯◯を△△に置き換え」のように、
  **何をどう変えるかを1句で**書く。先頭に `1.` `2.` と通し番号を付ける (「3は◯◯に」と返せるように)。

```markdown
| 修正内容 | 修正前 | 修正後 |
| -------- | ------ | ------ |
| 1. 「geom_bar」の後に「()」を追加 | `件数(geom_bar・…)` | `件数(geom_bar()・…)` |
```

- **単純な修正**と**TODO(検討事項)**を分ける。TODO は朱書きが「検討する」「必要か
  check」などと書いてあるもので、勝手に決めない。
- **読み取れない朱書きは推測しない。** 挿入記号だけで文字が無い、崩し字で読めない、
  前後とつながらない、といったものは 4.4 節の一覧に回す(作業を止めて逐一は聞かない)。

- **表を出したら，ターンを終える前に，次の 1 回分だけの先読みを起動する** (4.2 節)．

### 4.1 記録済みの修正案を順に出すとき

4.5 で `proposals_*.md` に記録した修正案を、ユーザに採否を聞きながら反映していくときの出し方。

**続きを頼まれたら、前回どこまで扱ったかを先に確かめる。** 既存の `proposals_*.md` と記録で最後に扱ったページを見て、その次のページから読む (最初のページから読み直さない)。

1. **章・節ごとに 5 件程度ずつ**出す (4 節の「提示の単位」．ユーザの指定があればそれに従う)。1回の返事で「OK」「3は◯◯に」と返せる量にする。
   見出しに「第5章 (`chapter_05.md`) 2/3: 節「…」」のように、章・ファイル・何回目か・節を書く。
2. **表の列は 4 節と同じ `修正内容 | 修正前 | 修正後` の3つ。** ページと行の列は出さない (位置は自分で控える)。
3. **番号は章の中の通し番号 (1, 2, 3…) で、「修正内容」の先頭に付ける。** `proposals_*.md` の
   内部番号 (`3-3` など) は出さない。返事の「3」が章番号と紛れないようにするため。
   **要判断の項目にも、単純な修正の番号に続けて数字を振る (20, 21, …)。`A`/`B`/`C` は使わない**
   (案の選択肢 `a`/`b`/`c` と取り違えるため)。選択肢だけを `a`/`b`/`c` にし、返事は「22a」の形で受ける。
   **単純な修正をすべて出して了承をもらってから、要判断に移る** (要判断を先に出さない)。
4. **修正箇所を目立たせる。** 修正前の列は消す部分を `~~打ち消し線~~`、修正後の列は足す・替える部分を
   `**太字**` にする。長い文は前後を `…` で省き、変わる部分の周りだけを見せる。
   「修正内容」の列は「「を強調」を削除」「「量」の前に「種類と」を追加」のように短く書く。
5. 気になる点 (朱書きどおりだと目安が消える・語が重複するなど) は、表の下に1-2行で書き、代わりの文案を添える。
6. **出す前に、修正前の文言が今の原稿にあるかを grep で確かめる** (行がずれていることがある)。
7. 反映は**章の分がそろってから**まとめて行う (反映の作業そのものは 4.2.1 のとおりエージェントに任せてよい)。置換リストを 任意の場所 (例: `_review/fixes_<ファイル名>.json`) に書いて
   `apply_fixes.py --apply` で当てる (`--post` は付けない。整形で直していない行や表まで動くため。付けてよい条件は 5 節)。
   差分の行数が件数と合うかを確かめてから、**章ごとに1コミット**する。
   表のセル幅が変わったときは `markdown-table-pad` をかけるが、**ファイル全体にかけると、
   直していない表 (もとから列がずれていた表) まで動く**。
   差分を見て、直した表以外が動いていたら、その表だけをそろえた形に戻す。
   ファイルを書き直すときは **BOM の有無を元のファイルに合わせる** (章ごとに違う)。

8. **要判断の項目は1件ずつ出す**。単純な修正とは扱いを変える。
   - 出す前に、その項目の**帯の画像 (`pNNN_bK.png`．黒文字＋朱書き) を送る** (`SendUserFile` が使えるときはそれで)。
     崩し字なら拡大 (`pNNN_zJ.png`) も送る。画像のローカルのパスも書く (クリックでは開けないため)。
   - 修正前 (原稿の文字どおり)・読み取った朱書き・案 a/b/c を出す。
     **おすすめの案は必ず a に置く**。理由を1行で添える。
   - 見出しには**全体の通し番号と章の中の番号の両方**を書く (例: 「要判断 9/50 (第5章 1/5)」)。
     残りの量が分かるようにするため。
   - 返事をもらったら、**その1件だけを反映して1コミットする**。
     そのあと次の1件を出す (反映とコミットを章でまとめない)。
   - 決着したら `proposals_*.md` のその項目に決定を書く。画像は消してよい (4.4 の扱い)。

```markdown
| 修正内容 | 修正前 | 修正後 |
|:--|:--|:--|
| 1. 「種類と」を「量」の前へ移す | 強調の量：~~種類と~~箇所数の絞り込み | 強調の**種類と**量：箇所数の絞り込み |
| 2. 「を強調」を削除 | 強調の対象：トピックセンテンス~~を強調~~ | 強調の対象：トピックセンテンス |
```

### 4.2 回答を待つ間に次の分を先読みする

**修正案を出してターンを終える前に、次に出す分の下ごしらえをバックグラウンドのエージェントに頼んでおく** (既定)。
ターンを終えると Claude は回答が来るまで動けないが、起動しておいたエージェントは動き続ける。
回答が来たら、反映してすぐ次の分を出せる。

- **先読みするもの**: **次の 1 回分だけ** (単純な修正 5 件程度，要判断なら次の 1 件)。帯の画像を読んで朱書きを読み取り、
  修正前の文言が今の原稿にあるかを grep で確かめ、4.1 節の形の表 (要判断なら案 a/b/c) まで作る。
  章の終わりなら次の章の先頭から。**それより先は先読みしない．** 章や本全体を一度に先読みすると，
  使うトークンが多いうえ，返事で方針が変わったときに無駄になり，読み違いの手戻りも増える。
- **書き出す先は `_review/marks/prefetch.md` だけ**。エージェントは**原稿・`proposals_*.md`・`pending.md` に書かない**。
  原稿を直すのは、本体と、4.2.1 の反映エージェントだけにする (先読みのエージェントは原稿に書かない)。
- **切り出し (`extract_marks.py`) は本体が先に済ませておく**。`manifest.tsv` は実行のたびに書き直されるので、
  エージェントは切り出し済みの画像を読むだけにする。範囲外の切り出しが要るなら、先読みはそこで止めて報告させる。
- **回答が来たら**: 今の分の反映は 4.2.1 のとおりエージェントに任せ (コミットはユーザの指示があるとき)、
  そのあいだに `prefetch.md` を読んで次の分を出す。
  - 出す前に、**修正前の文言をもう一度 grep で確かめる** (今の回答で同じ文が変わっていることがある)。
    当たらなくなった項目だけを読み直す。
  - 回答で方針が変わった (「この種の朱書きは全部◯◯に」など) ときは、先読みの該当する項目に当て直してから出す。
- 先読みがまだ終わっていなければ、待たずに自分で次の分を作り始めてよい (エージェントは止める)。
- **出す順序は先読みでも変えない**。単純な修正をすべて出して了承をもらってから、要判断に移る
  (4.1 節の 3)。先読みの下ごしらえも、単純な修正の残りを先に作り、要判断は後にする。
- **先読みの範囲は次の 1 回分に限り，1 つのエージェントには 1〜2 項目だけ渡す．** 大きな仕事を 1 つのエージェントに渡す
  (たとえば要判断 6 件をまとめて頼む) と，終わるまでが長く，回答を待つ時間に収まらない．
  要判断は **1 項目を 1 エージェント**にして，読み取り専用のエージェントを並列に走らせる
  (書き出す先は `prefetch_<範囲>_<項目>.md` のように項目ごとに分ける)。全章にまたがる語の方針のように 1 項目が重いときは，
  その 1 項目だけで 1 エージェントにする．
  同時に動かす数は **min(16, コア数−2) ÷ 2** を超えない。切り出し (`extract_marks.py`) は、本体が先に1回だけ済ませる。
- **先読みの項目に書かせること**: (1) 今の原稿での位置 (行番号．**直前の反映で行がずれるので，必ず今の原稿を grep し直させる**．
  複数箇所に当たるときは全部)，(2) 修正前 (原稿の文字どおり)，(3) 読み取った朱書きと，確度の低い点，
  (4) 前の変更との干渉，(5) 案 a/b/c (おすすめは a)，(6) 置換リスト用の old → new (複数行にまたがる置換は，前後の行を含める)，
  (7) 画像の絶対パス．
- **読み取り専用の先読みに，隔離 (`isolation: "worktree"` など) を付けない．** 絶対パスで読むだけの仕事なので不要で，
  別のリポジトリの作業でも，起動した側のリポジトリに使わない worktree とブランチが作られて，後始末が要る．
- **先読みの各項目に、反映済みかの判定を付ける。** 項目を `{"id","file","old","new"}` の配列にして
  `scripts/check_applied.py` に通すと、`applied` (反映済み)・`pending` (未反映)・`both` (一部だけ反映)・
  `moot` (別の直しで文が変わった．対象が消えた) が付く。
  `applied` は表に出さず「反映済み」の一覧にまとめ、`moot` は読み直して「対象外」か「要確認」にする。
  朱書きの PDF が新しい版になったとき、どこまで反映済みかを手で照合しなくて済む。
- **構造を変える項目の「影響」を先に調べておく。** 見出し・図・コードの削除・移動・番号の振り直しになる項目は、
  `scripts/impact.py` で、壊れる参照・繰り上がる図とコードの件数・関係する節を出し、要判断の表に「影響」の欄として添える
  (`impact.py label ラベル`・`range ファイル:開始-終了`・`text 文字列 --prose`・`figure 番号`)。
- **次の要判断の画像を先に送っておく。** いまの項目の返事を待つあいだに、次の 2〜3 件の帯・拡大の画像を
  まとめて送る (`SendUserFile`)。ユーザは返事を考えながら、次の項目を先に見られる。
- **提示の単位を、返事の様子で調整する。**
  - 単純な修正で「OK」が 3 回続いたら、次は 10 件ずつ (または同じ語・同じ型の置換は1項目にまとめて) 出すことを 1 行で提案する。
  - おすすめの案 a は、`decisions.json` (4.2.2) の**過去の選択の傾向**に合わせる
    (たとえば、専門語を残す選択が続いたら、専門語の判断は、まとめて出して「残す」をおすすめにする)。
- **ユーザが「先読みなし」と言ったら、その作業のあいだは先読みをしない**。

### 4.2.1 採否の反映は別エージェントに任せ，そのあいだに次の分を出す

ユーザが採否 (「OK」「3は◯◯に」) を返したら、**反映の作業はバックグラウンドのエージェントに任せ、
本体はそのあいだに次の分の提案を出す** (既定)。ユーザの次の判断を待たせない。

1. **採否を `decisions.json` に記録し、置換リストにする** (4.2.2)。
   `scripts/decisions.py add` で採否を記録し (承認した項目は `--status approved`、「直さない」は `rejected`)、
   `scripts/decisions.py to-fixes --ids ... --out fixes.json` で、承認済みの項目だけを `apply_fixes.py` の形式の置換リストにする。
   「ここは全部◯◯に」のような方針の返事は、該当する全箇所の項目まで展開して記録する。
2. **エージェントを1つ起動する** (機械的な作業向けのもの。判断は要らない)。エージェントには、次の3つを任せる。
   1. **置換の適用:** `scripts/apply_fixes.py fixes.json --apply` を走らせる (BOM・改行コード・「ちょうど1回」の確認は道具が行う。
      自分で置換のスクリプトを書かせない)。表のセルが変わるときは、**その表だけ**を列幅をそろえ直す (ファイル全体にはかけない)。
   2. **後始末:** `scripts/post_apply.py` を走らせる。コードの抽出ファイルの作り直し・図の再生成・点検スクリプトを、
      設定ファイル (`_review/marks/post_apply.json`) のとおりに行い、**意図していない図の書き換えは元に戻す**。
      図の再生成は1〜2分かかるので、ユーザが次の提案を読んでいるあいだに済む。
      設定ファイルの例 (`steps` の `when_changed` に当たる変更ファイルがあるステップだけが走り、`{changed}` にそのファイル名が入る):
      ```json
      {"steps": [{"name": "抽出ファイルの作り直し", "cmd": "python tools/extract_code.py {changed}", "when_changed": ["chapter_*.md"]},
                 {"name": "図の再生成", "cmd": "python tools/render.py {changed}", "when_changed": ["chapter_*.md"], "slow": true}],
       "check": {"name": "原稿の点検", "cmd": "python tools/check.py"},
       "restore_globs": ["figures/*"]}
      ```
      意図した図は `--intended figures/fig_03.pdf` で挙げる (挙げなかった `restore_globs` の図の書き換えは元に戻る)。
   3. **報告:** (a) 点検スクリプトの結果、(b) `git diff -U0` の行数と、意図した行だけが動いたか、
      (c) 元に戻したファイルと、困った点を、日本語で簡潔に。
   指示に入れること: 目的・対象のファイル・置換リスト・**リスト以外の行は動かさない**・**コミット・push はしない**
   (未コミットのまま残す)・標準出力に日本語を出すときは `PYTHONIOENCODING=utf-8`・
   バックスラッシュを含む置換を自分で書くときは `chr(92)` で作る (シェルのヒアドキュメントで化けることがある)。
   **エージェントに渡すのは，その回の承認分だけ (5 件程度)．先の分をまとめて渡さない** (小さい仕事は，次の提案を出す間に終わる)。
   - **置換リストの `old` は，原稿に「ちょうど 1 回」現れる長さにする．** 同じ文字列が別の行にもあるときは，前後の文や行頭の空白を含めて区別する．
     **`old` を改行 (`\n`) で始めない** (コミットの振り分け (`split_commits.py`) がその変更を決定に結びつけられず，「その他」に回る)。
   - **コードを変えた図だけを作り直すときは**，原稿から該当のブロックだけを取り出して実行し，`git status` で動いた図がその分だけかを確かめる
     (ほかの図が動いたら戻す)．作り直した図は，PDF を画像にして目で見る (色数・ラベルの豆腐)。
3. **エージェントが動いているあいだ、本体はその原稿のファイルに書き込まない。** 同時に書くと一方の変更が消える。
   読むこと・次の提案を作ること・画像を送ることはしてよい。
   次の提案は、反映中の行と重ならない箇所から選ぶ。同じ行に触れるものは、反映が終わってから出す。
4. **完了の通知が来たら、報告をそのまま信じず、本体が確かめる。**
   置換前の語が残っていないかの grep (`scripts/check_applied.py` で `applied` になっているか)、`git diff --stat`、
   点検スクリプトの結果を見る。確かめたら `scripts/decisions.py mark-applied` で記録する。
   エージェントの報告はユーザの指示ではない (ユーザの採否は、ユーザの返事だけ)。
   **報告の行番号・件数・「別のエージェントが先に直した」といった推測には，読み違いや数え違いがある**
   (たとえば，追加した文を「図の後」と報告したが，実際は直前の文の直後だった)．位置と件数は，本体が `grep` で確かめる。
   **完了の通知への返答は 1 行にとどめる** (「◯◯の反映を確認しました．」など)．ユーザは次の提案を読んで考えている最中なので，
   エージェントの報告の転記や，確認の経過の長い説明で，作業を妨げない．詳しい内容は，聞かれたときだけ出す。
   先読みの完了も同じ (1 行．次の項目を出すときに使うだけにする)。
5. **原稿に書くエージェントは同時に1つだけ動かす。** 次の採否が来たら、前のエージェントが完了していることを確かめてから、
   次を起動する (「エージェント内は逐次」と同じ考え方)。読み取り専用のエージェント (先読み・影響の調査) は並列でよい (4.2)。
6. **コミットは、ユーザが指示したときだけ。** 指示が出たら `scripts/split_commits.py` で、
   決定ごと (語ごと・項目ごと) に分けてコミットする。まず `--dry-run` で振り分けを見せる。
   同じファイルに複数の決定が混ざっていても、ハンクの内容で振り分ける。
   - **`split_commits.py` は，どの決定にも結びつかない変更も，「その他の変更」として最後の 1 コミットにまとめる．**
     「この方針の分だけ」のように**一部だけ**をコミットしたいときに，そのまま実行すると，関係の無い変更まで入る
     (対象の決定だけを別ファイルにして `--file` で渡しても，「その他」は最後にコミットされる)。
     **一部だけをコミットするときは `--skip-other` を付ける** (`other` をコミットせず未コミットのまま残す)。
     先に `--dry-run --skip-other` で `other` の行を確かめる。
     決定に結びつかない粒度 (1 ハンクの中の一部の行など) で分けたいときは，`git diff -U0` のハンクを行範囲で選び，
     `git apply --cached --unidiff-zero` でステージして 1 コミットずつ作る
     (作る前にステージが空であること，作った後に対象外の変更が入っていないことを確かめる)。
     `--skip-other` を付けずに実行してしまったときは，`git reset --mixed HEAD~1` で，変更を残したまま取り消す (push の前なら影響はない)。
   - **節ごとに分けるとき**も同じ方法で，節はコードブロックの外の見出し (`##`・`###`) で判定する．
     コードと，そこから作る図 (生成元と生成物) は 1 コミットにし，進捗の記録は原稿と分けて最後に置く。
7. ユーザが「バックグラウンドにしないで」と言ったときだけ、本体が反映する。
   件数が少なくても，この既定は省かない (数件でも別エージェントに任せる)。

### 4.2.2 決定の記録 (`decisions.json`)

採否は `_review/marks/decisions.json` に記録する (`scripts/decisions.py`)。記録しておくと、次のことができる。
- 承認済みの項目だけを置換リストにする (4.2.1 の 1)。
- 反映したかの確認と、コミットの振り分け (4.2.1 の 4・6)。
- 提示の単位とおすすめの案を、過去の選択の傾向に合わせる (4.2)。

```json
{"decisions": [
  {"id": "K18", "tag": "flow", "label": "「フロー」を「流れ」にする", "status": "approved",
   "files": ["figures/a.png"],
   "items": [{"file": "chapter_08.md", "old": "フローの", "new": "流れの", "count": 1}]}
]}
```

`status` は `pending` (採否待ち)・`approved` (承認済み．未反映)・`applied` (反映済み)・`rejected` (直さない)。
`tag` は、コミットを分ける単位 (語・章・項目のまとまり)。`files` は、本文の置換ではなく丸ごと差し替わるファイル (図など)。
`rejected` の記録も残す (「直さない」と決めた箇所を、あとで蒸し返さない。傾向の判断にも使う)。

```bash
D=C:/.../apply-proof-marks/scripts      # スキルのスクリプトのあるディレクトリ
python $D/decisions.py add --id K18 --tag flow --label "「フロー」を「流れ」にする"     --items-json '[{"file":"chapter_08.md","old":"フローの","new":"流れの"}]' --status approved
python $D/decisions.py list --status approved
python $D/decisions.py to-fixes --ids K18,K19 --out fixes.json     # 承認済みだけが出る
python $D/apply_fixes.py fixes.json --apply
python $D/decisions.py mark-applied --ids K18,K19
python $D/split_commits.py --dry-run                                # コミットの振り分けを見る
python $D/split_commits.py --group-by-tag --tag-label "contrast=対比の表現をそろえる"   # 同じタグの決定を1コミットにまとめる
```

`--file` (記録の置き場) は、サブコマンドの前に置く。`to-fixes` に `pending`・`rejected` の id が混ざっていると、警告を出して飛ばす。
`split_commits.py` は、既定では1決定=1コミットにする。`--group-by-tag` を付けると、同じ `tag` の決定を1コミットにまとめる
(メッセージは、そのタグの最初の決定の `label`。`--tag-label タグ=メッセージ` で指定できる)。
`split_commits.py` は、ステージ済みの変更があると実行を拒否する。同じ行に2つの決定の変更が入っていて1つのハンクになるときは、
ハンクを分けられないので、先に載っている決定へ寄せて警告を出す (その行は、決定を分けて反映しておく)。
`check_applied.py` は、`file` が読めない項目を `nofile` と判定する。

### 4.3 時間のかかる作業は、バックグラウンドで行うことを提案する

判断の途中で、**時間のかかる作業** (データの取得と集計・図やコードの作り直し・図の再生成・
調べもの) が入るときは、その場で進めて回答を待たせず、**バックグラウンドのエージェントで行うことを提案する**。
ユーザが「バックグラウンドで」と言ったら、エージェントに任せて、そのあいだに次の項目を出す。

- 提案は1行で、**何を・どこへ書くか・原稿に触れないこと**を添える
  (例: 「データの取得と遷移の集計をバックグラウンドで進めます。結果は `_review/marks/` に置き、原稿は触りません」)。
- エージェントには、原稿を直接編集させない・コミットさせない。結果は報告用のファイルに書かせる。
  原稿への反映は、要判断が終わってから本体が行う
  (ただし 4.2.1 の反映エージェントは、渡した置換リストの範囲だけ原稿を直してよい)。
- 返事を待つだけで済む短い作業 (数分以内) は、バックグラウンドにしなくてよい。

### 4.4 判読不明点を一覧にして引き継ぐ

**修正案を出せなかった朱書き**は、質問して終わりにせず、`_review/marks/pending.md`
に記録してから次に進む。

- 各項目に**黒文字と朱書きの両方が写った画像**(`pNNN_bK.png`。`_clean`/`_ink` は
  文字だけ・朱書きだけに分離した版なので不可)の**絶対パス**を添える。
  ユーザーが自分の目で確かめ直せるようにするため。
- **修正の提案をこちらから出さない限り、その画像は削除しない。**
  `extract_marks.py` を別ページで再実行しても、一致しないファイルは残るのでそのままにする。
  `rm -f` でまとめて掃除するときも、`pending.md` に載っている画像は対象から外す。
- 次にこのスキルを使うときは、`pending.md` を先に読む。
  - ユーザーから修正案が出た項目、あるいは今回の作業で解決した項目は表から消す。
  - 今回新たに見つかった判読不明点を追記する。
  - こうして常に「**まだ手つかずの朱書き**」だけが残る一覧になる。
- 作業の最後には、**このセッションで新たに見つかったものと、`pending.md` に残っていた
  既存の未対応分をまとめて**、表とパスの一覧としてユーザーに示す。

`pending.md` の書式例。

```markdown
| 章 | ページ | 帯 | 画像(黒文字+朱書き) | 何が分からないか |
| -- | -- | -- | -- | -- |
| 第9章 | p.41 | b3 | `D:/.../marks/p041_b3.png` | 「一定額」の前の1文字挿入。崩し字で判読不能 |
```

### 4.5 記録だけするときは，判断が要る箇所の画像をそろえておく

「修正はあとで．記録だけ」と言われたら，原稿には手を入れず，修正案をファイルに書いて終える．
あとでユーザが**画像を見て判断する**ので，そのための画像を先に作っておく．

1. 対象の範囲を，**判断用の画像まで一度に**切り出す．

   ```bash
   python ${CLAUDE_SKILL_DIR}/scripts/extract_marks.py <校正PDF> \
       --pages 79-180 --clean always --ink always --zoom
   ```

   - `--zoom` は書き込み1つごとに 300dpi の拡大 (`pNNN_zJ.png`) を出す．崩し字・挿入記号の行き先・
     小さな印 (U 字の削除の印など) は，拡大で見ないと決められないことが多い．
   - `manifest.tsv` は実行のたびに書き直されるので，**切り出しは1回にまとめてから**読み取りに入る
     (読み取りを並列のエージェントに分けるときも，切り出しは先に1回だけ)．
2. 修正案を `marks/proposals_pXXX-YYY.md` に書く．章ごとに「単純な修正」(表) と「要判断」と
   「本全体にかかる指示」に分ける．
   - 「要判断」の各項目には，修正前 (原稿の文字どおり)・読み取った朱書き (確かでない点も書く)・
     修正案 a/b/c・**画像の絶対パス**を付ける．画像は，帯 (`pNNN_bK.png`．黒文字＋朱書き) を必ず入れ，
     読み取りに使った `_clean`・`_ink`・`_zJ` も添える．
   - 画像は，その項目が決着するまで消さない (4.4 と同じ扱い)．
3. 報告では，件数 (単純・要判断・本全体) と `proposals_*.md` のパスを示す．
   判断の場面では，要判断の項目を**1件ずつ**，表と画像 (帯と拡大) を一緒に出す．

### 5. まとめて適用する

(本体が直接当てない．4.2.1 節のとおり，別エージェントに任せる．)

置換リストを JSON にして一括で当てる。1件ずつ Edit を呼ぶより速く、
**検索文字列がちょうど1回現れることを全件確かめてから書く**ので部分適用にならない。

```bash
python ${CLAUDE_SKILL_DIR}/scripts/apply_fixes.py fixes.json          # 確認
python ${CLAUDE_SKILL_DIR}/scripts/apply_fixes.py fixes.json --apply
```

`--post` を付けると sentence-per-line・markdown-table-pad・`check_manuscript.py` (カレントにあるときだけ) まで走る。
ただし整形はファイル全体にかかり、直していない行や表まで動くので、**原稿がすでに整形ずみ (差分が直した行だけに収まる) と分かっているときだけ**付ける。
付けないときは、直した行と表だけを `sentence-per-line`・`markdown-table-pad` で個別に整える。

- **本体は polish-loop の `scripts/apply_fixes.py`** (このスキルの `apply_fixes.py` はそれを呼ぶ入口)。
  polish-loop のスキルが同じ置き場に無いと動かない。キー名は `old`/`new` でも `before`/`after` でもよい。
- 1件でも当たらなければ何も書かずに止まる。このスキルでは `--partial` を付けず、原因を確かめてから直す
  (polish-loop は付けて回す)。
- **確認の出力に並ぶ前後の文脈と警告を、必ず見てから `--apply` する。**
  `count`・警告・`--strict`・CRLF/BOM の扱いは polish-loop の SKILL.md の 3 節にあり、ここでは繰り返さない。
  ページをまたぐ一括置換は、先に対象語のあるページの朱書きを確かめる (「落とし穴」)。

コードブロックや図を変えたときは、別途、図の再生成とコードの採番の振り直しを行う(`render-figures` などの道具があれば回す)。

### 6. 漏れを確かめて記録・コミット

適用後、その章の範囲でもう一度 `--list` を走らせ、帯の数と処理した件数が合うかを見る。

`--pages` を付けると **朱書きの無いページを名指しで出す**。

```
朱書きのあるページ: 11
[56, 57, 58, 59, 62, 64, 65, 66, 67, 70, 71]
帯: 22 本 (1ページあたり 2.0)
朱書き無し: 60,61,63,68,69 (指定 16 ページ中 5)
```

ページ番号が飛んでいても、これで**見落としたのか元から無いのか**が区別できる。
飛びを自分で数えない。

`pending.md` に項目が残っていれば、4.4 節のとおり一覧とパスを示す。
無ければ「判読不明点なし」とだけ report する。

**体裁・位置の指示は、PDF を組み直して朱書きと見比べるまでが1つの作業**。
文字列の置換と違い、直したつもりで直っていないことがある。

- ある記録では、**写真2枚が1ページに入るときの間隔**と**目次の体裁**が
  「何度指示しても直っていない」と**2度差し戻された**。置換の件数は合っていたが、
  組み上がりを見ていなかったため気づけなかった。
- したがって、**位置・間隔・目次・表紙まわりの指示を含むときは**、
  適用 → **PDF を再生成** → **その朱書きのページと組み上がりを1枚ずつ見比べる**
  → 直っていない項目を一覧にする、まで済ませてから report する。
- 見比べていないのに「反映しました」と報告しない。**見比べた枚数を報告に書く**。

そのうえで記録・コミットする。

### 7. 朱書きを「正解データ」として残す

**手順5で作った `fixes.json` を捨てない。** これは**ユーザ自身が下した評価**の記録で、
AI の推敲レビューが当たっていたかを測る唯一の材料になる。

同じ原稿を `polish-loop` で推敲していれば、両者を突き合わせて
**見逃し**(朱書きだけが挙げた)と**空振り**(AI だけが挙げた)を出せる。

```bash
python ${CLAUDE_SKILL_DIR}/../polish-loop/scripts/calibrate.py \
    --ai fixes_r3.json --human fixes.json --baseline <朱書き反映の直前の原稿>
```

キー名は `old`/`new` のままでよい(`calibrate.py` が両形式を受ける)。
詳しくは `polish-loop` の手順9。**朱書きの `fixes.json` は章ごとに残しておく**。

## 画像 (スキャン・写真) から読むとき

朱書きが `/Ink` 注釈ではなく、**紙に書いてスキャンした画像**や**朱書きを焼き込んだ画像**しか無いときは、
画像をそのまま渡す。拡張子 (jpg/png/tif など) で画像の方法に切り替わる。

```bash
python ${CLAUDE_SKILL_DIR}/scripts/extract_marks.py _review/scan/*.jpg --zoom          # 赤ペン (既定)
python ${CLAUDE_SKILL_DIR}/scripts/extract_marks.py _review/scan/*.png --color green --min-sat 0.75
```

**複数ページの TIFF** は全ページを読み、帯の名前は `<名前>_p1_b1`・`<名前>_p2_b1` …になる。
`--ref-pages` は画像・ページを渡した順に対応させる (`12,11` なら 1 つ目が参照の 12 ページ)。

**紙をスキャンした PDF** (注釈が無く、ページが画像だけ) をそのまま渡しても、自動でこの方法に切り替わる
(各ページを元の解像度で描画して色で探す。帯の名前は `pNNN_bK`)。`--color` などはそのまま効く。
注釈も無く、本文の文字がある普通の PDF では切り替えず、「Ink 注釈がありません」と注意だけ出す。

**スマホの写真**もそのまま渡せる。3つを自動で直す。

- **向き**: 横倒し (本文の行が縦に走る) なら反時計回りに 90° 回す。EXIF に向きが入っていなくても行の縞で見分ける。
  **上下は見分けられない**ので、帯が逆さに出たら `--rotate 270` (角度は反時計回り。`0` で回さない)。
- **解像度**: 写真の EXIF は 72dpi のことが多い。72dpi 以下なら A4 の長辺に写っているとみなして見積もり直す
  (4032 画素なら約 345dpi)。帯の上下の余白 (`--pad`) が正しい幅になる。
- **彩度の下限**: EXIF に機種名がある (カメラで撮った) 画像は既定を **0.30** にする (スキャンは 0.40)。
  写真の赤ペンは薄く写り、0.40 では遠くの細い取り消し線を落とした。

出力は PDF のときと同じ `marks/` に、`<画像名>_bK.png` (帯)・`_ink.png` (`--ink always`)・`_zJ.png` (`--zoom`) の形で出る。
以後の手順 (4 節から) は変わらない。

**PDF の注釈から読むときとの違い** (読み取れる指示そのものは同じで、違いは探し方と確かめ方)。

| | Ink 注釈 (PDF) | 画像 (色) | 画像 + `--ref` |
|---|---|---|---|
| 朱書きの探し方 | 注釈の座標．誤検出なし | **色**．図・コードの色付け・写真の同じ色も帯になる | **もとの原稿との差**．図の色は拾わない．赤以外のペンも拾う |
| 小さな印 (点1つ) | 拾う | 画素が少ないと捨てる (`--min-pixels`) | 同左 |
| 字に重なった朱書き | `_clean` で元の字を戻せる | **戻せない**．`_clean` は作らない | **戻せる** (参照の画像が `_clean`) |
| 拡大 (`--zoom`) | 300dpi で描き直す | 元の画像の解像度が上限 | 同左 |
| 読む量 | 帯だけ | ほぼ同じ (誤検出の帯の分だけ増える) | ほぼ同じ |

### もとの原稿 (参照 PDF) と比べる: `--ref`

**印刷したときの PDF が手元にあれば**、`--ref` で渡すと色ではなく差で探す。

```bash
python ${CLAUDE_SKILL_DIR}/scripts/extract_marks.py _review/scan.pdf --ref manuscript.pdf            # ページ番号どうしを対応
python ${CLAUDE_SKILL_DIR}/scripts/extract_marks.py p07.jpg p29.jpg --ref manuscript.pdf --ref-pages 7,29
```

- 参照のページを描画し、特徴点 (ORB + RANSAC) で大まかに、ECC で細かく位置を合わせ、
  スキャンにあって参照に無いものを朱書きとする。紙の端 12pt (スキャナの影) は外す。
- **OpenCV が要る** (`pip install opencv-python`)。無ければ止まって案内が出る。1ページに数秒かかる。
- **印刷したときと同じ版**でないと、直した箇所がすべて差になる。本文の重なりが 80% 未満のページは
  「位置が合わない」と出して色の方法に戻る。
- 実測 (200dpi のスキャン 5ページ・正解 26 か所): 見つかる数は色と同じ (赤ペン 24・緑 25)。
  違いは、図の色を拾わないこと・青のペンも拾ったこと・`_clean` で朱書きの下の字が読めること。
- **写真は台形にゆがむので合わないことが多い** (スキャン向け)。合わなければ色に戻るだけで害はない。

- **誤検出の帯は、画像を見て外す。** 色で探す以上、図の同じ色相は避けられない。
  デジタルの朱書き (彩度がほぼ最大) なら `--min-sat 0.7〜0.8` で図の中間色の多くが外れる。
  紙の赤ペンは彩度が下がる (スキャンで 0.4〜0.6 あたり) ので、既定から上げすぎない。0.70 では取り消し線や囲みが落ちた。
- **スキャンは 300dpi 以上にする。** 朱書きの下の字は戻せないので、取り消し線の範囲や
  重なった字は解像度だけが頼り。170dpi では本文は読めるが、重なりの判定は苦しくなる。
- **黒や青のペンは色で探せない** (本文の黒・リンクの青と区別できない)。朱書きは赤・緑などの彩度の高い色で書く
  (`--ref` なら黒や青も拾える)。
- 書き込みの多いページは、帯がページ全体の1本にまとまる。これは PDF のときも同じで、
  そのページは丸ごと読むことになる。

## 落とし穴

- **段落や節の終わりの右に何度もなぞった「┘」形の印は，ユーザの「読み終わり」の印**．
  修正の指示ではないので，要判断に上げずに読み飛ばしてよい．
- **朱書きの漢字は，前後の語と合わせて読む．** 「技量」の前の2文字を「失敗」と読んだが，
  実際は「実験」(→「実験技量」) だった．挿入先の語とつながる読みを先に試す．
- **「〜は?」のような質問の朱書きは，修正の指示ではない．** 答えを書き，案は「原稿は変えず答えだけ (おすすめ)」
  「コードにコメントを足す」「地の文に足す」の形で出す．ユーザの返事 (たとえば「数をそろえる．奇数が望ましければ 7」) が，そのまま案になることもある。
- **朱書きが特定の箇所ではなく，語そのものを指すとき** (「◯◯は基本的に使わない」「◯◯は△△のような表現を検討」)は，全章の語の方針．
  先読みの 1 項目として，全章の該当行を一覧にし (ファイル・行・全文・種別・言い換え案)，要判断として 1 回で出す (機械置換はしない)．
  **同じ語でも意味で分ける**: 言い換えると意味が変わる行 (たとえば，量や順序を「読み取る」意味の「読めません」を「区別できません」にする) は
  そのまま残し，意味が同じ行だけを直す．境界例は別に挙げて，ユーザに選んでもらう．
  図題や図のタイトルなど，同じ文言が 2 か所にある行は，同じ文にそろえる (文字列だけの変更なら，図は作り直さない)。
- **返事が「12 色では」のように，番号と直す語だけのとき**は，その項目だけを直し，ほかの項目は了承と受け取る．
  直した後の文を示して，意図と合うかを確かめてもらう。
- **ツールの落とし穴**: シェルツールにヒアドキュメントで渡す Python に `del x[i:j]` と書くと，削除コマンドと誤認されて実行が止まることがある．
  スライスへの代入 (`x[i:j] = []`) で書く。

- **一括置換の前に、その語がある全ページの朱書きを見る。**
  「効く」という語を全体で言い換えたところ、**7箇所で朱書きの指示と違う語に直して
  しまった**(第11章4件・第15章・第16章・付録)。
  ページをまたぐ一括置換は、対象語のあるページの朱書きを先に確認してから行う。
- **コードブロックを章間で移すときは、仮のコード ID を付けない。**
  `code_08_06_R2` のような仮 ID を付けると、採番の道具が**その上に正式な ID を
  挿入**して2行並ぶ。ID の行ごと消してから移し、採番は採番の道具に任せる。
- **朱書きが figure の上にあることもある。** 図そのものへの指示(「Python と同じに」
  「少し大きく」)は原稿の文字列ではなくコードを直す。置換リストではなく個別に扱う。
- **章の境界は朱書きページの並びからは分からない。** 必ずコード ID で確かめる。
- **重なりの判定は帯全体で測らない。** 5行の帯の中で3文字に線を引いただけでは、
  帯全体に対する比率は 1% にしかならず見逃す(実測で 0.007〜0.012)。
  **筆跡の矩形の中だけで測る**と同じ帯が 0.29〜0.49 になる。`stroke_overlap()` がこれ。

## スクリプト

| `scripts/impact.py` | 見出し・図・コードを動かす判断の影響 (壊れる参照・繰り上がる番号) を調べる |

### extract_marks.py の主な引数

| 引数 | 既定 | 意味 |
| ---- | ---- | ---- |
| `--pages` | 全部 | `56-71` や `88,90` |
| `--dpi` | 170 | 切り出しの解像度。日本語の本文が読める下限がこのあたり |
| `--pad` | 18 | 帯の上下に足す文脈(pt)。本文1行 ≒ 14pt |
| `--list` | — | 画像を作らず一覧だけ。`--pages` 併用で朱書きの無いページも名指しで出る |
| `--clean` | auto | 朱書きを消した版も出す(`auto`/`always`/`never`) |
| `--ink` | auto | 朱書きだけを白地に置いた版も出す(同上) |
| `--overlap` | 0.10 | `auto` の閾値。**筆跡ごと**の重なり率の最大値で判定する |
| `--zoom` | — | 書き込み1つごとに拡大も出す |
| `--zoom-dpi` | 300 | `--zoom` の拡大の解像度 |
| `--out` | 入力のあるフォルダの `marks/` | 出力先。別の PDF・画像の出力を上書きしたくないときに分ける (上書きするときは知らせる) |
| `--color` | red | 画像のみ。朱書きの色 (`red`/`orange`/`green`/`blue` か `#rrggbb`) |
| `--hue-tol` | 25 | 画像のみ。色相の許容幅 (度) |
| `--min-sat` | 0.40 (写真は 0.30) | 画像のみ。彩度の下限 (0-1)。図の中間色を外すときは上げる |
| `--min-pixels` | 30 | 画像のみ。これより画素の少ない帯は捨てる (にじみ・ごみ) |
| `--rotate` | auto | 画像のみ。反時計回りに回す角度 (`0`/`90`/`180`/`270`)。auto は横倒しなら 90 |
| `--ref` | — | 画像・スキャンのみ。もとの原稿の PDF。色ではなく差で探す (OpenCV が要る) |
| `--ref-pages` | — | `--ref` の対応ページ (画像・ページの順)。既定はスキャンと同じ番号、画像は 1 から |

## 前提

- `pypdf`、`pypdfium2`(ページの描画)、`Pillow`、`numpy`(重なりの判定に使う)。
  すべて `pip install pypdf pypdfium2 pillow numpy` で入る(poppler は要らない)。
  `--ref` を使うときだけ `opencv-python` も要る
- **Windows では `PYTHONIOENCODING=utf-8` を付けて実行する。** 付けないと標準出力の
  日本語が cp932 で化け、`朱書き無し:` の行が読めない。
- **Read ツールで校正 PDF を直接開かない。** 25MB を超えると
  「password-protected」という誤った理由で失敗する(実際は暗号化されていない)。
  ページを見たいときも `extract_marks.py` の帯の画像か、pypdfium2 で描画したものを見る。
- 朱書きが **`/Ink` 注釈**として PDF に入っていること。
  画像として焼き込まれている場合・紙をスキャンした場合は、色で探す (スキャンした PDF は自動で切り替わる)
  (「画像 (スキャン・写真) から読むとき」の節)。
